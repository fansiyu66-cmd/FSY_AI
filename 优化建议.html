IDENTICAL 脚本流畅度优化清单

36max1.lua · 帧率与卡顿专项分析 · 共 20 项优化建议

这份脚本的瓶颈不在算法复杂度，而在两个典型的性能反模式：
① 同一件事被多条路径重复做（三条钓鱼按钮恢复逻辑、两条 RestoreMobileFishingButtonUI、多个技能扫描循环）；
② 每帧都做属性查找 / 字符串拼接 / 跨 C++ 边界调用（GetAttribute、Config["ESP_"..cat]、FindFirstChild 链）。
下面的优化按 ROI（投入产出比） 从高到低排序。

详细优化项
01
钓鱼按钮「三重冗余守护」

问题当 Config.AutoCast == false 时，钓鱼按钮的守护显示逻辑同时存在于 三处：

  • Heartbeat 里每 0.25s 触发 RestoreMobileFishingButtonUI(false)
  • RenderStepped 里又写一遍 cachedMobileFishBtn.Visible = true
  • BindToRenderStep("IdenticalForceFishBtnVisible", Last, ...) 再写一份

也就是说，关闭自动抛竿后每帧至少 2 次属性赋值，0.25s 还会触发潜在的全屏扫描。

建议只保留 BindToRenderStep 那处（它本就是为压制原版每帧隐藏而设计，优先级最高）。删除 RenderStepped 中的重复块，Heartbeat 只保留状态清零。所有赋值改为「变化才写」：

if cachedMobileFishBtn.Visible ~= true then cachedMobileFishBtn.Visible = true end
if cachedMobileFishBtn.Active ~= true then cachedMobileFishBtn.Active = true end
02
GetMobileFishingButton 缓存命中条件太苛刻

问题当前判断：

if cachedMobileFishBtn and cachedMobileFishBtn.Parent and (includeHidden or cachedMobileFishBtn.Visible) then
    return cachedMobileFishBtn
end

当原版脚本每帧隐藏按钮时，Visible 会不断变成 false，导致缓存永远失效、每次都要重扫全屏。

建议

  • 判活只保留 cachedMobileFishBtn and cachedMobileFishBtn.Parent，Visible 交给外部守护逻辑
  • 两次全屏扫描之间加 3~5 秒节流，失败后指数退避
  • 扫描时改用 GetChildren() 只走 ScreenGui 的直接子控件，不用 GetDescendants
03
Heartbeat 里连续读取 4 次 GetAttribute

问题

local isFishing  = char:GetAttribute("Fishing") == true
local isCD       = char:GetAttribute("CDForTheNextThrow") == true
local isMinigame = char:GetAttribute("Minigame") == true ...
local isSwimming = char:GetAttribute("Swimming") == true

GetAttribute 涉及 C++ → Luau 边界，每帧 4 次很浪费。

建议用 AttributeChanged 缓存到局部变量：

local attrFishing, attrCD, attrMinigame, attrSwimming = false, false, false, false
char.AttributeChanged:Connect(function(name)
    if name == "Fishing" then
        attrFishing = char:GetAttribute("Fishing") == true
    elseif name == "CDForTheNextThrow" then
        attrCD = char:GetAttribute("CDForTheNextThrow") == true
    end
end)

在 CharacterAdded 时重新绑定即可。

04
DoesInstanceMatchNPCSpec 是 O(NPC × Specs) 的两层循环

问题雷达每 1.25s 对每个 NPC 实例遍历 27 个 ImportantDialogueNPCs，每个还要 GetCompiledSpecKeywords 再逐个别名查找。

建议

  • 建立 反向索引：一次扫描把 spec → keywords 全展开成 keyword → specList 的 map，扫描时先用 inst.Name:lower() 做 hash 查表命中
  • summary 缓存已有 30s 有效期，但不要用 GetDescendants() 构造，只取第一层 ProximityPrompt / TextLabel + Humanoid.DisplayName
  • 对同一个 NPC 匹配后 break 出 loop
05
RefreshAllESPNow 每 0.25s 的字符串拼接 + 无条件赋值

问题

local isEnabled = (Config["ESP_" .. data.espCategory] == true)

每次拼新字符串产生 GC 压力。

建议

  • 建预编译 map 复用：
local ESP_CATEGORY_KEYS = {
    GodSpirit = "ESP_GodSpirit",  SecretRod = "ESP_SecretRod",
    Boats     = "ESP_Boats",      Maoshan   = "ESP_Maoshan",
    Taoist    = "ESP_Taoist",     Boss      = "ESP_Boss",
    Players   = "ESP_Players",
}
local isEnabled = Config[ESP_CATEGORY_KEYS[data.espCategory]] == true
  • 距离用平方距离比对，且只在变化 ≥1 米时刷新文字
  • 只有在任一 ESP 分类开启时才跑刷新循环，否则 skip
06
GetCachedSkillButton 每 2 秒全量 Descendants

问题每隔 2 秒会把 fUI / Fisher_GUI / MainGui 的 Descendants 全走一遍，每个按钮再跑 DoesButtonMatchSkillKey（内部还 GetDescendants + 遍历兄弟节点）。

建议

  • 技能面板 DOM 很少变，用 fUI.DescendantAdded / DescendantRemoving 增量维护，不做周期性全扫
  • DoesButtonMatchSkillKey 删除 d:GetDescendants() 兜底分支，只查 Name + Text + 一层 Parent 兄弟 TextLabel
  • 缓存生命周期与 cachedFUI 绑定，Fisher_GUI 重建时清空
07
IsCharacterHoldingFishingRod 每帧调用

问题函数内部遍历 char:GetChildren()（每个 Model / Tool），未找到 Tool 时还要遍历 Backpack:GetChildren() 找鱼竿。

建议

  • 缓存结果，只在 char.ChildAdded/Removed、Backpack.ChildAdded/Removed 时更新
  • 或缓存 0.2s 到期后再重判断
08
TryFavoriteProtectedFish 每 3 秒遍历整个背包

问题Heartbeat 每 3 秒触发，函数内部对 Inventory / Hotbar 每个 item 跑 IsFishItemFavorited（遍历子节点）+ ShouldProtectFishItem（多个子节点 + Attribute）。

建议

  • 改增量队列：Inventory.ChildAdded / Hotbar.ChildAdded 时给新 item 打一次检查，push 到待办队列
  • 周期任务只处理这个待办队列，不重扫全背包
  • 已经发过 FavoriteItem 的 item 用 lastLockSentAt[item] 记录后，整个 item 从待扫名单剔除
09
SafeSellAllFish 循环内重复校验

问题逐条卖鱼时每次 IsSellPacketArgBlacklisted(normalItem) + IsSellPacketArgBlacklisted(normalItem.Name) 都做纯字符串匹配，可能递归到 HasAnyProtectedFishInBag。

建议

  • 循环前扫 sellableItems 时把 safe 布尔写入 item 的弱表缓存，循环内不再二次校验
  • HasAnyProtectedFishInBag 不要每次新建 containers 表，直接用已 Scan 好的 protectedPureSet
10
DismissStuckPromptsAndRestore 被多次并发调用

问题Heartbeat 每 1.25s 无条件调用一次，外层 while 又在 IsDialogueUIOpen 前后各调一次，TriggerNPCInstancePrompts 内部还有 delay 0.18/0.3 各一次，触发对话瞬间会连开 4~5 次。

建议

  • 加 0.5s 节流门（lastDismissTime），并发触发直接 return
  • forceScanAll 的 Workspace:GetDescendants() 只在启动 / 手动点击时执行，雷达循环只走 originalPromptState 已有条目
11
BindVerticalCanvas 为每个子项挂 2 个属性变化监听

问题

child:GetPropertyChangedSignal("AbsoluteSize"):Connect(requestRefresh)
child:GetPropertyChangedSignal("Visible"):Connect(requestRefresh)

配合 UIListLayout.AbsoluteContentSize + scrollFrame 的 2 个信号，每个 page 上子控件的信号累计可达上百条。

建议

  • 只保留 AbsoluteSize（Visible 变化基本伴随尺寸变化）
  • requestRefresh 节流窗口从 0.08s 放宽到 0.15s
  • measureContentHeight 直接信任 layout.AbsoluteContentSize.Y + extraPadding，不再逐项 AbsoluteSize 累加
12
UI 构建函数中 Tween 对象滥用

问题createToggleRow、createDropdownRow、createButtonRow、createNPCDualActionRow、CreateDashCard 等都在函数入口一次性创建 2~4 个 TweenService:Create 对象。UI 上 100 个 toggle 就常驻 400 个 Tween 实例。

建议

  • 改成懒创建（第一次点击时才建）
  • 复用单一 TweenInfo 常量（TweenInfo 本身也可缓存）
  • 高频场景（ESP 距离文字、通知卡）不要建 Tween，直接赋值
13
ShowNotification 频繁 Tween + task.delay

问题每次通知 TweenService:Create 两次（滑入 + 滑出）+ 一次 task.delay。MAX_NOTIF_CARDS = 4 下每 3~5 秒产生 6~8 个新 Tween。

建议

  • 反向 Tween 前先检查 card.Parent，避免销毁后播放抛错
  • 通知卡改用对象池（3~4 个 slot 预建，切换文本 + 重播 Tween），避免 Instance.new + Destroy 抖动
14
while isRunning 常驻循环即使功能关闭也在跑

问题四个常驻循环：0.25s ESP 刷新、1.25s 雷达、0.5s Dashboard 更新、3s 钓鱼按钮守护。功能全部关闭时仍占用 CPU。

建议

  • 全部改成按需启动：功能开启时才 task.spawn 并保存循环引用，关闭时 task.cancel
  • 用统一 Scheduler 中心只维护「是否还有活」的依赖集合
15
RefreshGuiAndDataRefs 每 0.4s 大量 FindFirstChild

问题每次执行 4~6 次 FindFirstChild 链：

cachedMainGui = cachedPG:FindFirstChild("MainGui")
cachedFUI = (cachedMainGui and cachedMainGui:FindFirstChild("Fishing"))
    or (cachedPG and cachedPG:FindFirstChild("Fishing"))
    or (fisherGui and fisherGui:FindFirstChild("Fishing"))
cachedBossBar = cachedFUI and cachedFUI:FindFirstChild("BossFightBar")

建议改事件驱动：PlayerGui.ChildAdded/Removed 更新 cachedMainGui / cachedFUI，cachedFUI.ChildAdded/Removed 更新 cachedBossBar。缓存命中条件简化成「只要 cachedFUI 存活就返回」。

16
IsDialogueUIOpen 兜底分支遍历所有 Gui 的 Descendants

问题当 priorityGuis 为空时，兜底分支会对每个可见 Gui 顶层子控件跑 GetDescendants()。商店/背包面板有几百个子控件，一旦进兜底代价非常高。

建议

  • 记住上一次命中的 cachedDialogueNode，Parent 未销毁就不重新找
  • 兜底分支限制只查可见 ScreenGui 顶层前 3~5 个 GuiObject
  • 或用 getconnections 挂 PlayerGui.DescendantAdded，命中对话弹窗就缓存
17
GetPureFishName / patternCache 满容量直接 clear

问题pureNameCache 容量满 512 时 table.clear，导致新名字的缓存全失效，触发新一轮 hash 分配（patternCache 256 同理）。

建议

  • 满时用简单 LRU 剔除（记录 lastUsed 时间覆盖最旧的 1/4），比 clear 更平滑
  • 或容量提到 1024，配合弱表
18
__namecall Hook 里用非 plain 模式 find

问题

if action == "Out of bar" or action == "Out of bar (overpull)"
    or action:find("Out of bar") or action:find("Fail") or action:find("Miss") then

find 未指定 plain=true 会走 Lua pattern 引擎，慢于 plain 模式。若服务端频繁推 FishingMinigame，每帧都可能跑一次。

建议常量提到上值，使用 :find(str, 1, true) plain 模式。

19
异步 InvokeServer 可能 yield 永久挂起

问题

task.spawn(function()
    pcall(function() rem:InvokeServer(unpack(args)) end)
end)

InvokeServer 会 yield 等服务端返回，如果服务端不返回则协程永久占着调度槽。

建议给异步 Invoke 加超时兜底（如果 RemoteFunction 支持），或直接改 FireServer（多数场景服务端不关心返回值）。

20
activeConnections 数组无限增长

问题table.insert(activeConnections, ...) 分布在 Radar / BindVerticalCanvas / 每个 Toggle 里。UnloadScript 会清理，但运行时没有任何回收机制，Destroy 后的连接不会自动从数组移除。

建议

  • 用 { conn = c, alive = true } 包装
  • 或每个循环启动时把旧连接 Disconnect()，避免残留
一句话总结 这份脚本的瓶颈不在算法复杂度，而在 「同一件事多路重复做」（三条钓鱼按钮恢复、两条 RestoreMobileFishingButtonUI、两个技能扫描循环）和 「每帧都做属性查找 / 字符串拼接」（GetAttribute、Config["ESP_"..cat]、FindFirstChild 链）。

把上述重复路径合并 + 事件化缓存后，同等场景下 Heartbeat 的工作量大约能砍掉 50%~70%，帧率抖动会明显改善。
